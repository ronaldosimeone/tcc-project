## How to read this

* **Identification vs majority class.** Six of the nine failures are air leaks, so a retriever that always lands on the generic main-compressor chunk (WAP-5 p. 170, which happens to contain the delivery-hose task 601.3M.02) scores the majority accuracy without identifying anything. Balanced identification and the dryer/oil column are the honest measures.
* **Why sensor evidence cannot name the failure here.** The online RCA blames `Oil_temperature` / `Motor_current` / `DV_pressure` for air leaks, the dryer fault and oil leaks alike: the sensors are shared by every component, so the sensor→component vocabulary (RF-35) maps all of them to the same compressor chunks. The query carries no type information to retrieve.
* **Why the corpus cannot either.** The indexed corpus is a *scheduled* maintenance schedule (25 chunks, 3–6 tasks each): it says what to inspect periodically, not which symptom points to which fault. There is no fault-finding table to retrieve, so even the `oracle` queries rarely clear the similarity cut.
* **RN-04 is doing its job.** In the production setup the assistant abstains on these cases instead of producing a confident procedure from irrelevant context, and no citation is fabricated. Abstention is the correct output for a corpus that does not contain the answer; it is not a diagnosis.
* **Consequence for the platform.** Failure *detection* is the ML layer's job (see docs/metropt2_unseen_failures.md); failure *type* identification is not supported by the current corpus and must not be claimed. Closing the gap needs (a) a fault-finding / troubleshooting document for the APU and (b) task-level chunking, both re-evaluated with this same benchmark.
